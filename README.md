# Cascade Hunter — محاكاة 100 دولار

Python 3.11 أو أحدث.

- `binance_cascade_hunter.py`: الكود الأصلي كما ورد، دون تعديل.
- `binance_cascade_hunter_paper.py`: محاكاة برصيد أولي **100 USDT**، تستخدم بيانات Binance USDT-M العامة وإشارات الكود الأصلي. لا تحتاج مفاتيح API ولا ترسل أوامر حقيقية.

## التشغيل

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python binance_cascade_hunter_paper.py
```

على Windows، أمر التفعيل: `.venv\Scripts\activate`.

لبدء حساب افتراضي جديد بقيمة 100 USDT، مع استبدال سجل المحاكاة السابق:

```bash
python binance_cascade_hunter_paper.py --reset
```

تظهر التعبئة الافتراضية والرصيد في الطرفية، مع ملخص كل 30 ثانية. تُحفظ المراكز والرصيد وسجل الصفقات في `paper_state.json` وتُستعاد تلقائيًا عند إعادة التشغيل. للإيقاف اضغط `Ctrl+C`. شغّل عملية واحدة فقط لكل ملف حالة. لا تتم مراقبة المراكز أثناء توقف البرنامج؛ عند العودة تُطبق قواعد الخروج على الأسعار الجديدة.

## ما يبقى كما هو

BTC وETH وSOL، رافعة حسابية 50x، تخصيص 85% من الهامش المتاح، عتبة الحركة 1.2%، تضاعف الحجم 3.5، ضغط دفتر الأوامر ±0.35، هدف 1.8%، وقف 0.9%، وفاصل 8 ثوانٍ. ترث المحاكاة منطق الإشارات والدخول والخروج من الملف الأصلي مباشرةً. لم تُصحح خصائص الاستراتيجية الأصلية، ومنها استخدام الشمعة الجارية واحتساب الهدف والوقف من سعر الإشارة. أما ربح الحساب الافتراضي فيُحسب من أسعار التعبئة الافتراضية الفعلية عند فتح الصفقة وإغلاقها.

يحجز الحساب هامش كل مركز ويمنع استخدام الرصيد نفسه في المراكز المتزامنة. الرافعة تدخل في حجم المركز، ولا تُضرب بها الأرباح مرة ثانية. الرصيد `wallet` يشمل الربح والخسارة المحققة والعمولات، و`equity` يضيف الربح والخسارة غير المحققة من آخر أسعار متاحة، و`free` هو الرصيد المتبقي بعد حجز الهامش. لا يُستخدم الربح غير المحقق لتمويل صفقات جديدة.

## حدود المحاكاة

هذه محاكاة حسابية وليست Binance Testnet، وليست اختبارًا تاريخيًا أو دليلًا على الربحية. تفترض التعبئة بسعر `last` عند جلبه، ولا تحاكي عمق التنفيذ أو الانزلاق أو التمويل أو التصفية أو شرائح هامش الصيانة. لذلك قد تستمر صفقة افتراضية بعد النقطة التي كانت ستُصفّى عندها فعليًا، وقد يصبح الرصيد سالبًا عند فجوة سعرية. يتوقف فتح صفقات جديدة عندما لا يكفي الهامش. الهدف والوقف يُراقبان بالاستطلاع كما في الأصل، وليسا أوامر حماية على المنصة، ويؤثر تعطل بيانات السوق في المراقبة.

عمولة المحاكاة الافتراضية **0.05% لكل تعبئة** افتراض قابل للتغيير، وليست قراءة لعمولة حساب Binance. لتعطيلها:

```bash
python binance_cascade_hunter_paper.py --state paper_state_no_fees.json --fee-rate 0
```

عند تغيير إعدادات الاستراتيجية أو العمولة، استخدم ملف حالة جديدًا أو `--reset`. الملف الأصلي يحتوي مسار تداول حقيقي؛ أمر المحاكاة المذكور أعلاه هو ملف التشغيل المقصود هنا.

**هذه نتيجة نسخة تقريبية وليست اختبارًا مطابقًا للبوت الأصلي:**

- شرط ضغط دفتر الأوامر معطّل لعدم توفر بياناته التاريخية. بقية عتبات الإشارة والرافعة والحجم والهدف والوقف مأخوذة من الأصل.
- تُحسب الإشارة بعد إغلاق الدقيقة، ويحدث الدخول عند افتتاح الدقيقة التالية. تختلف هذه الطريقة عن مراقبة الشمعة الجارية كل 1.2 ثانية في الأصل.
- الهدف والوقف محسوبان من سعر إغلاق شمعة الإشارة، كما يستخدم الأصل سعر الإشارة. تفترض المحاكاة الخروج عند لمس الهدف أو الوقف داخل شمعة الدقيقة؛ الوقف أولًا إن لُمسا معًا. عند وجود فجوة تُستخدم قيمة الافتتاح. هذا نموذج خروج من OHLC، وليس إعادة بناء للاستطلاع اللحظي أو تنفيذ مضمون عند سعر الوقف.
- رصيد واحد مشترك؛ عند تزامن الإشارات تكون الأولوية BTC ثم ETH ثم SOL. لا تستخدم أرباحًا لاحقة داخل الدقيقة لتمويل دخول عند افتتاحها، ولا تعيد الدخول في شمعة الخروج نفسها. تُغلق المراكز المتبقية عند نهاية الفترة لأغراض التقرير.
- العمولة المفترضة 0.05% لكل تنفيذ، وقواعد تقريب الكمية وحدودها مأخوذة من بيانات المنصة الحالية؛ ليست إعادة بناء للقواعد التاريخية.
- لا يحاكي الاختبار التمويل أو الانزلاق أو التصفية أو هامش الصيانة. التراجع محسوب عند إغلاق كل دقيقة، وقد يكون التراجع داخل الدقيقة أكبر. لا تكفي 4 صفقات للحكم على ثبات الاستراتيجية.

## النسخة الثانية: مسح ديناميكي لأعلى 40 عملة

- `binance_cascade_hunter_dynamic.py`: الكود الجديد المرسل كما هو، في اسم مستقل ليبقى البوت الأول محفوظًا. يحتوي مسار أوامر حقيقية عند وضع مفاتيح الحساب وتشغيل هذا الملف.
- `binance_cascade_hunter_dynamic_paper.py`: نسخة محاكاة تبدأ بـ100 USDT افتراضي، وتراقب الإشارات باستمرار عبر WebSocket، دون مفاتيح API أو أوامر حقيقية.

تشغيل المحاكاة الجديدة:

```bash

```

تختار أعلى 40 رمزًا مطابقًا لصيغة `/USDT:USDT` حسب حجم آخر 24 ساعة، وبحد أدنى 15 مليون USDT. تراقب شموعها عبر WebSocket، وتتحقق من دفتر الأوامر عند تطابق الحركة والحجم. أول إشارة يكتمل فحصها وتستوفي الشروط تحصل على المركز المتاح؛ لا تنتظر تجميع إشارات جميع العملات أو ترتيبها حسب القوة. يبقى حد المركزين والهامش المشترك كما هو. تبقى الرافعة 50x والحجم 85% والهدف 1.8% والوقف 0.9% كما في الكود المرسل. **شرط دفتر الأوامر فعّال** في هذه المحاكاة التي تستخدم بيانات السوق الحالية.

تُحدّث قائمة أعلى 40 كل 600 ثانية، بينما تعمل مراقبة الإشارات طوال الوقت على تحديثات شموع الدقيقة الجارية من WebSocket. لا يوجد انتظار عشر دقائق بين فحوص الإشارات. تراقب المخارج كل 8 ثوانٍ حتى للمراكز التي خرجت عملاتها من القائمة. قد يتأخر الدخول والخروج بسبب الشبكة أو حد المركزين أو قفل الحساب. يبقى سعر الإشارة مرجعًا للهدف والوقف كما في الأصل.

تُحفظ حالة النسخة الجديدة في `paper_state_dynamic.json` وتُستعاد تلقائيًا، بصورة منفصلة عن حالة البوت الأول. لتصفير هذه المحاكاة فقط:

```bash

```

تستخدم المحاكاة محرك الحساب الافتراضي نفسه: حجز الهامش، عمولة مفترضة 0.05% لكل تنفيذ، عرض الرصيد، حفظ الصفقات، وإيقاف نظيف بواسطة `Ctrl+C`. لا يحاكي الحساب التمويل أو الانزلاق أو التصفية، ولا تتم مراقبة المراكز أثناء توقفه. شغّل عملية واحدة لكل ملف حالة. ملفات الحالة بين النسختين غير قابلة للتبادل.

## تحديث المحاكاة إلى المراقبة المستمرة

أُضيف `continuous_scanner.py` وأصبح ملف تشغيل المحاكاة نفسه يستخدمه تلقائيًا. ملف الاستراتيجية الحقيقي `binance_cascade_hunter_dynamic.py` ما زال محفوظًا بمنطقه الأصلي؛ التغيير يخص تشغيل المحاكاة الحية.

- تجلب REST آخر 30 شمعة لكل رمز عند البدء، ثم تتابع التحديثات عبر `wss://fstream.binance.com/market/stream`.
- تتأكد من شروط الحركة والحجم أولًا، ثم تتحقق من أعلى 20 مستوى لدفتر الأوامر عبر REST. حد فحوص الدفتر هو مرة في الثانية لكل رمز وأربع بدايات طلبات في الثانية إجمالًا. بقية طلبات CCXT تخضع أيضًا لمحدد المعدل.
- تنفذ أول فرصة يستوفي فحصها الشروط دون انتظار فحوص العملات الأخرى. توجد 8 مهام فحص مع دمج تحديثات الرمز المكررة، وحد المركزين ومنع تكرار المركز وقفل الرصيد. لا تضمن التقاط كل حركة أو تنفيذًا فوريًا بلا تأخير.
- ترفض الإشارات المتقادمة بأكثر من 10 ثوانٍ، وتعيد فحص الإشارة بعد وصول دفتر الأوامر وبعد الحصول على قفل الحساب.
- عند انقطاع البث أو فقد شمعة تعيد الاتصال وتجلب الشموع قبل قبول إشارات جديدة. يبقى مراقب الخروج منفصلًا عبر REST، مع تأثره بتوفر الشبكة. عند تعذر تهيئة رمز تعيد محاولة تهيئته بعد نحو 30 ثانية.
- تحافظ على `paper_state_dynamic.json` والرصيد والمراكز الموجودة. لا يتطلب التحديث `--reset`، ولم تتغير شروط العتبات أو العمولة أو الرافعة. يبدأ فاصل تحديث القائمة من وقت تشغيل البرنامج.

لتحديث النسخة داخل Ubuntu في Termux، أوقف العملية القديمة بـ`Ctrl+C` أولًا حتى تحفظ حالتها، ثم:

```bash
cd ~/Final
source .venv/bin/activate
git pull --ff-only
python -u binance_cascade_hunter_dynamic_paper.py 2>&1 | tee -a live-paper.log
```

تظهر رسالة `CONTINUOUS WATCH CONNECTED` عند اتصال البث، و`CONTINUOUS STATUS` كل 30 ثانية مع عدد التحديثات وفحوص الدفتر والدخول. إذا بقي الاتصال متعذرًا لا تدخل المحاكاة من إشارات قديمة؛ راجع رسالة إعادة الاتصال. الشبكة وسرعة الهاتف وتحديثات المنصة تؤثر في التأخير.

نتائج الاختبارات التاريخية المحفوظة تخص الجدولة السابقة كل عشر دقائق، ولم تُعد محاكاتها للمراقبة المستمرة. زيادة تكرار المراقبة لا تثبت زيادة الربحية.

ملف الإعدادات والاستراتيجية الجديدة هو `binance_cascade_hunter_dynamic_v2.py`، وملف تشغيل المحاكاة هو **`binance_cascade_hunter_dynamic_v2_paper.py`**. تبقى المراقبة المستمرة عبر WebSocket، وتحديث قائمة أعلى 40 كل 10 دقائق، وشرط دفتر الأوامر، ومراقبة الخروج كل 8 ثوانٍ، والعمولة الافتراضية 0.05% لكل تنفيذ كما هي.

**تفسير الوقف:** استُخدمت 15% كحركة سعرية من سعر الإشارة، بنفس أساس الـ0.9% السابقة؛ ليست خسارة 15% من الهامش أو من الحساب. عند إشارة شراء 100 يكون الوقف 85، وعند إشارة بيع 100 يكون 115. في حالة تطابق سعر التعبئة مع الإشارة، تعادل هذه المسافة 750% من هامش الصفقة عند 50x قبل الرسوم، أي 75% من المحفظة لصفقة هامشها 10% منها. قد تختلف الخسارة الفعلية في النموذج بسبب الفجوات والتأخر واختلاف سعر التعبئة.
